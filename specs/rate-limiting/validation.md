## Two flagged claims — verified

1. **wrangler.jsonc limits match spec's retuned values.** Confirmed: `wrangler.jsonc` declares `CHAT_RATE_LIMITER` (5/60s), `AUTH_RATE_LIMITER` (5/60s), `MUTATION_RATE_LIMITER` (30/60s) — exactly matching spec.md's US-002/US-003/US-004 acceptance criteria and plan.md §4's table. `worker-configuration.d.ts` types all three as `RateLimit` on `Env`. No mismatch.

2. **No `useQuery`/`useMutation` call sites exist anywhere in the app.** Confirmed via `grep -rn "useQuery\|useMutation" src` (excluding the bridge's own tests) — zero matches. The mutating API routes (transactions/categories/recurring-templates) are called exclusively via `src/lib/ai/tools/client.ts` using the plain `fetch`-based `src/lib/ai/fetch.ts` wrapper, not TanStack Query. Their errors surface through the pre-existing inline tool-call error UI (`tool-call-display-state.ts`'s `"error"` state), never through the new `QueryCache`/`MutationCache` toast bridge. This is accurately described in spec.md's Open Questions and tasks.md's us005-01 note — **and it means US-005's acceptance criterion, taken literally ("via the app's existing global toast error handling"), is not met for the mutation-write surface.** It is met in spirit (the user does see a distinguishable error), just through a different, pre-existing channel than the one the AC names.

## Drift Findings

### Unmet requirements (spec → code)

- **US-005 (Should Have) — mutation-write surface:** 429s from transactions/categories/recurring-templates routes never reach `toastManager` because nothing in the codebase calls those routes via `useQuery`/`useMutation`. They surface via the inline tool-call error UI instead. This was correctly self-flagged during implementation (tasks.md us005-01, spec.md Open Questions) rather than silently glossed over — but as validated, it is a genuine AC miss, not a documentation nuance.
- **US-005 (Should Have) — auth surface:** no test verifies that a 429 response from `/api/auth/*` (shaped as `{error:{name,status},message}` by this feature's `toErrorResponse`) is correctly parsed by `authClient.signIn.social()` (better-auth's client) and surfaced via `login-page.tsx`'s existing `toastManager.add` call. This wasn't caught by the implementer's own note (which only flagged the mutation surface) — it's a second, independently-discovered gap. The risk is real: better-auth's client generally expects its own error envelope shape, and this route intentionally short-circuits before ever reaching `auth().handler()`, returning this app's custom envelope instead. Whether that parses cleanly into a user-legible message is unverified in either direction.

### Scope creep (code → spec)

- `.gitignore:8` gained `.env.production` — not mentioned in plan.md's Affected Modules, unrelated to rate limiting. Trivial and harmless, but not spec'd.
- `src/routes/api/auth/$.ts:8` — `request.headers.get("CF-Connecting-IP") ?? "unknown"`. plan.md's Technical Decision ("IP extraction via `CF-Connecting-IP`") explicitly says "No fallback header chain," addressing only the choice not to fall back to `X-Forwarded-For`. It does not mention this `"unknown"` sentinel for a **missing** header entirely. Practically low-risk (Cloudflare's edge always sets this header in production) but means any request that somehow lacks it — local dev, unusual proxying — would share one rate-limit bucket with every other such request. Undocumented in plan.md/spec.md.

### Plan deviations

- None of substance. `worker-configuration.d.ts` re-generation produces byte-identical bindings/content; the only diff against a fresh `vp run wrangler:type` was whitespace style, already reconciled by the project's formatter in the committed version.

### Convention drift

- None found. `RateLimitedError` follows the existing `AppError` subclass pattern precisely (matches `UnauthorizedError`'s shape). `apiHandler`'s opt-in `rateLimit` option preserves default behavior for every existing GET call site (explicitly tested). Chat and auth routes' inline (non-`apiHandler`) checks match plan.md's documented rationale for why those two routes are exempt from the wrapper.
