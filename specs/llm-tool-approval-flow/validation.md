## Independent Library Verification (plan.md §6 claim)

Plan.md §6 claims `needsApproval`/`addToolApprovalResponse` is a fully native, unmodified `@tanstack/ai@0.28.0` mechanism. Verified independently via Context7 (`/tanstack/ai`), not by trusting the plan:

- `needsApproval: boolean` is a documented `ToolDefinition` field; `addToolApprovalResponse({id, approved})` is a documented `ai-client`/`ai-react` method. Confirmed.
- The published `ToolCallState` type is exactly `'awaiting-input' | 'input-streaming' | 'input-complete' | 'approval-requested' | 'approval-responded' | 'complete' | 'error'` — matches `getToolCallDisplayState`'s switch exactly.
- Docs explicitly confirm: _"In case of an `output-error` result, the tool-call part transitions to an `error` state"_ — this directly supports the code's `denied ⟺ state === 'error' && approval.approved === false` derivation (plan.md §6's riskiest inference).
- One narrative doc page (`architecture/approval-flow-processing.md`) uses the informal phrase _"Denied approvals lead to a 'cancelled' state"_ — this does **not** correspond to any actual `ToolCallState`/`ToolResultState` enum value (neither type has a `'cancelled'` member per their own reference pages), so it reads as loose prose describing the outcome, not a real third state the code needs to handle. Noted for completeness, not treated as a defect.
- Docs did **not** explicitly confirm that `approval.approved` survives the transition into the `error` state unmodified — this is the one part of plan.md §7's own risk register that remains an inference rather than a documented guarantee, even after this research.

### Plan deviations

- **plan.md internal inconsistency, not a code defect:** plan.md §1 Overview says "flag the **12** mutating tool definitions," but plan.md §5's own table and the actual code list **11** (3 categories + 3 transactions + 5 recurring templates), with **6** read-only tools left unset (not 5). The orchestrating instructions for this validation also assumed 12/5. Code is internally consistent with §5's table and with spec §2's tool list — only the §1 prose count is wrong. Cosmetic; worth a one-line `/revise` fix to plan.md so future readers aren't misled, but does not affect the verdict.
- **The end-to-end integration task (us002-02) was verified by code-tracing and `vp check`/`vp test run` only — no live click-through against a running LLM conversation.** This is explicitly flagged by the task itself and by plan.md §7 as a required follow-up before the feature is "fully verified," and it was not done in this implementation pass. This is the most consequential open item: the single most safety-critical acceptance criterion in the whole feature (US-003 — a denial must reach the LLM and the conversation must continue rather than dead-end) rests entirely on inferred/library-documented behavior, confirmed by this validation's Context7 research but never observed running in this app.

### Convention drift

None. Compound-component namespace pattern preserved (`ChatMessages.X`); no `createContext`/provider introduced, matching the explicit "reject Context" decision in plan.md §6; only pre-existing `--color-caution`/`--color-info` design tokens used, no new tokens.
