# Plan: LLM Tool Approval Flow

**Spec:** [./spec.md](./spec.md)
**Mode:** brownfield
**Status:** Approved
**Created:** 2026-07-11
**Version:** 1.2

---

## 1. Overview

The installed tool-calling SDK, `@tanstack/ai@0.28.0` (with `@tanstack/ai-client@0.16.3` / `@tanstack/ai-react@0.15.4`), already ships a native human-in-the-loop mechanism — a `needsApproval` flag on `toolDefinition()` and an `addToolApprovalResponse()` client method — that does exactly what spec §5–§6 requires: pausing execution mid-stream, resuming on decision, and auto-feeding a denial back to the LLM as a tool result. This plan does **not** introduce any new pause/resume machinery, server route, or persistence. The work is three narrow, additive changes: (1) flag the 11 mutating tool definitions with `needsApproval: true`, (2) build a new `ToolCall` compound component — in its own file, `src/components/ui/tool-call.tsx`, split out of the now-oversized `chat-messages.tsx` — as a context provider (`ToolCall.Root`) exposing a generic `displayState`/`statusLabel`/approve-deny actions to small, focused children, with per-state visual styling driven by a `data-tool-call-state` attribute and Tailwind `group-data-*` selectors rather than a JS style-lookup map, and with **zero dependency on `@tanstack/ai` types** — the mapping from the library's `ToolCallPart` to this component's generic contract lives in a separate helper, `src/lib/ai/tool-call-display-state.ts`, that only the route calls (see §6 for the full rationale, superseding this plan's v1.0 "plain props, no Context" decision and refining v1.1's Context design further), and (3) remove the now-redundant "narrate deletes in text" system-prompt instruction (spec §7). See spec.md §2 Goals for the full requirement list this satisfies.

## 4. Data Models

Spec §5 defines two conceptual entities, `ToolCall` and `Approval`. Neither becomes a new persisted or hand-rolled type — both map directly onto the tool-calling library's existing `ToolCallPart` type, which this feature does not modify. The genuinely new contract this feature introduces is a **client-side derived display state**, computed from `ToolCallPart` at render time.

### ToolCallPart (existing library type, `@tanstack/ai` — unmodified)

| Field       | Type                                                                      | Notes                                                                                                                                                                                                                     |
| ----------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type`      | `'tool-call'`                                                             | Discriminant on `UIMessage.parts`.                                                                                                                                                                                        |
| `id`        | string                                                                    | Stable per proposed call.                                                                                                                                                                                                 |
| `name`      | string                                                                    | Tool name, e.g. `create_transaction`.                                                                                                                                                                                     |
| `arguments` | string (JSON)                                                             | Proposed input; finalized (`input-complete`) before an approval request ever fires — satisfies spec US-001's "proposed arguments visible before deciding."                                                                |
| `state`     | `ToolCallState`                                                           | `'awaiting-input' \| 'input-streaming' \| 'input-complete' \| 'approval-requested' \| 'approval-responded' \| 'complete' \| 'error'`                                                                                      |
| `approval`  | `{ id: string; needsApproval: boolean; approved?: boolean } \| undefined` | Present only for tools defined with `needsApproval: true`. `approved` is set by `addToolApprovalResponse` and is the durable record of the user's decision — it persists after the state moves past `approval-responded`. |
| `output`    | `any \| undefined`                                                        | Populated once a result exists (success or the library's auto-generated denial error).                                                                                                                                    |

**Business rules (from the library, load-bearing for this feature):**

- A `ToolCallPart` only ever reaches `state === 'approval-requested'` if its originating `toolDefinition()` was declared with `needsApproval: true`. Read-only tools (no such flag) never enter this state — satisfies spec US-001's "read-only calls unaffected."
- Once `addToolApprovalResponse({ id, approved })` is called for a given `approval.id`, the library immediately transitions `state` away from `'approval-requested'` and the decision cannot be re-triggered (no further approval UI can render for that id) — satisfies spec's "Approval cannot be changed" rule (§5) without any plan-level bookkeeping.
- Each `ToolCallPart` in a turn carries its own independent `approval.id`; resolving one does not affect sibling parts in the same message — satisfies spec US-005 directly from the library's design, no extra state management needed.
- On denial, the library auto-produces a tool result (`{ error: "User declined tool execution" }`, `state: "output-error"`) and feeds it to the LLM as a normal tool-result message — satisfies spec US-003's "LLM must be informed of denial" with no custom glue code.

### ToolCallDisplayState (new — derived, client-only, not a stored field)

A pure function of `ToolCallPart` — `getToolCallDisplayState(part: ToolCallPart): ToolCallDisplayState` — this is the actual new "domain" contract this feature adds. As of v1.2, this function (and its sibling `getToolCallStatusLabel(displayState): string | undefined`) live in `src/lib/ai/tool-call-display-state.ts`, **not** in the UI layer — `ToolCallDisplayState` itself is the only piece of this contract `src/components/ui/tool-call.tsx` knows about; it's the component library's own exported type, not derived from `ToolCallPart`. The route calls both functions once per tool-call part and passes the results (`displayState`, `statusLabel`) as plain props to `ToolCall.Root`, which then (a) uses `displayState` to drive its own `Collapsible` open state, (b) stamps it onto the DOM as `data-tool-call-state` for CSS-driven color (see §6), and (c) exposes both values to descendants via `ToolCallContext`.

| Display state         | Derivation rule                                                                    | Rationale                                                                                                                                                                                                                                                           |
| --------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pending-approval`    | `part.state === 'approval-requested' && part.approval`                             | Drives whether the approval-actions child renders itself.                                                                                                                                                                                                           |
| `denied`              | `part.state === 'error' && part.approval?.approved === false`                      | The library represents denial as a generic `error` state; `approval.approved` distinguishes intent from failure (see §6).                                                                                                                                           |
| `error`               | `part.state === 'error' && part.approval?.approved !== false`                      | Either a non-gated tool's genuine failure, or a post-approval execution failure — existing error rendering, unchanged per spec §7 constraint.                                                                                                                       |
| `running` (existing)  | any of `awaiting-input \| input-streaming \| input-complete \| approval-responded` | `approval-responded` is a brief transient state (library immediately re-streams for continuation) — folded into the existing "running" treatment rather than given its own UI, since it is not user-actionable and typically resolves within one stream round-trip. |
| `complete` (existing) | `part.state === 'complete'` or `part.output !== undefined` with no error           | Unchanged.                                                                                                                                                                                                                                                          |

**Domain invariant:** a `pending-approval` card must render its arguments without requiring an extra click to expand, and its Approve/Deny decision must be a single interaction (spec NFR, Usability). Both are satisfied by `ToolCall.Root` computing its own `Collapsible` open state from the `displayState` prop it's given (see §6) — no external caller needs to know this rule exists, and `ToolCall.Root` itself needs no knowledge of `ToolCallPart` to satisfy it.

### ToolCallContext (new — the compound component's Context value, fully generic)

Following the `PromptInputContext` shape already established in this codebase, split into `state`/`actions`. Unlike v1.1, **no field here references `ToolCallPart` or any `@tanstack/ai` type** — this is the component library's own, self-contained contract:

| Part                 | Shape                  | Notes                                                                                                                                                                                                     |
| -------------------- | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `state.displayState` | `ToolCallDisplayState` | Passed into `ToolCall.Root` as a prop by the caller (already mapped from whatever the caller's data source is); every descendant reads it from here.                                                      |
| `state.statusLabel`  | `string \| undefined`  | Passed into `ToolCall.Root` as a prop by the caller; the copy for `ToolCall.StatusBadge` to show (`undefined` renders nothing — e.g. for `complete`). The library never hardcodes state-to-text mappings. |
| `actions.approve`    | `() => void`           | Bound to the `onApprove` prop given to `ToolCall.Root`; `ToolCall.ApprovalActions` calls this directly — no id ever reaches a descendant component.                                                       |
| `actions.deny`       | `() => void`           | Same, for denial.                                                                                                                                                                                         |

**Business rules:** none — by design, this context carries no domain data at all, only the generic state enum, its display label, and two bound callbacks. All actual content (tool name, arguments, response, error/denial copy) flows through ordinary `children`, passed by the caller directly into each leaf component (`ToolCall.Name`, `ToolCall.Args`, `ToolCall.Response`, `ToolCall.DeniedNotice`, `ToolCall.Error`) — never through context, and never derived from a `ToolCallPart`-shaped object inside `tool-call.tsx`. `ToolCall.Root` is the only component that constructs the context value; every other `ToolCall.*` component consumes it via `use(ToolCallContext)`.

## 6. Technical Decisions

### Rely entirely on the library's native approval mechanism

**Decision:** Use `needsApproval` + `addToolApprovalResponse` as-is; build no custom pause/resume, queueing, or approval-tracking logic.
**Alternatives considered:** A custom middleware layer intercepting tool calls before execution (relevant if the installed SDK lacked approval support — it doesn't).
**Rationale:** Confirmed against the installed package's shipped types/JS and Context7 docs for `/tanstack/ai` (not assumed from a newer API) that this version fully implements pause-on-approval, per-call independent resolution, and automatic denial-to-LLM feedback — exactly the spec's requirements.
**Tradeoffs accepted:** The feature is coupled to this library's exact state-machine shape (`ToolCallState` union, `approval` field). If the SDK's approval API changes in a future major version, the rendering switch and `ToolCallDisplayState` derivation will need to move with it.

### Derive "denied" from `approval.approved === false`, not from the error string

**Decision:** Distinguish a denied call from a genuinely failed call using `part.approval?.approved === false`, not by matching the literal string `"User declined tool execution"`.
**Alternatives considered:** String-matching the auto-generated error message (fragile — an internal library string, not a documented contract) or introducing a synthetic client-side "denied" `ToolCallState` (not possible without forking the library's type).
**Rationale:** `approval.approved` is a structured field set exactly once by `addToolApprovalResponse` and is documented to persist on the part; it is unaffected by SDK copy changes. Satisfies spec US-003's requirement that denied is "distinguishable from a completed or errored call." This derivation logic lives in exactly one place — `getToolCallDisplayState(part)`, called once by `ToolCall.Root` (§4, §6) — so `ToolCall.DeniedNotice` and `ToolCall.Error` both read the same already-computed `displayState` from context rather than each re-deriving it.
**Tradeoffs accepted:** This is an inference from the library's architecture docs (approval field is set once, only mutated by the approval response), not an explicitly documented invariant of the `error`-state transition. `/task` should include a quick manual verification (deny a call, inspect `part.approval` in the rendered state) before relying on it in tests or review.

### Model the approval UI as a Context-backed compound component, in its own file, styled via `data-*` + `group`

**Decision (supersedes plan v1.0 — see Changelog):** `ToolCall` moves to its own file, `src/components/ui/tool-call.tsx`, as a compound component backed by `ToolCallContext` (§4). `ToolCall.Root` is the sole provider: it takes `displayState`, `statusLabel`, `onApprove`, `onDeny`, `children`; sets `className="group"` and `data-tool-call-state={displayState}` on its rendered `Collapsible.Root` element; and provides `{ state: { displayState, statusLabel }, actions: { approve, deny } }` via context. Every other `ToolCall.*` component takes **no data props of its own** (only `children` for content, `className` for layout overrides) — it calls `use(ToolCallContext)` and either self-guards (renders `null`) or renders unconditionally, and gets its per-state color from Tailwind `group-data-[tool-call-state=x]:` selectors rather than a JS style-lookup object. The full contract (revised in v1.2 — see the next decision for why content moved to `children` and the color map was replaced by a dedicated `StatusBadge`):

| Component                  | Props / children                                                 | Context usage                                             | Self-guard condition                                                                                                              | Styling mechanism                                                                                                                         |
| -------------------------- | ---------------------------------------------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `ToolCall.Root`            | `displayState`, `statusLabel`, `onApprove`, `onDeny`, `children` | provider; also reads its own `displayState` prop          | always renders; owns `Collapsible` open state, forced true while `displayState === 'pending-approval'`, otherwise user-controlled | sets `group` class + `data-tool-call-state` attribute; border/bg via `group-data-[tool-call-state=error]:border-negative/40` etc.         |
| `ToolCall.Name`            | `children` (the tool name)                                       | `state.displayState` (icon/chevron styling only, no text) | always renders                                                                                                                    | icon color via `group-data-[tool-call-state=x]:text-*`; renders `children` as-is, no interpretation of what the name means                |
| `ToolCall.StatusBadge`     | none                                                             | `state.displayState`, `state.statusLabel`                 | renders `null` if `statusLabel` is falsy                                                                                          | spinner vs. static dot chosen by `displayState === 'running'` (the library's own enum value, not external data); color via `group-data-*` |
| `ToolCall.Content`         | `children` (pure layout)                                         | none                                                      | always renders                                                                                                                    | unchanged                                                                                                                                 |
| `ToolCall.Args`            | `children` (formatted arguments text)                            | none                                                      | renders while `children` is truthy                                                                                                | static styling, no state-dependent color                                                                                                  |
| `ToolCall.ApprovalActions` | `approveLabel?`, `denyLabel?` (default "Approve"/"Deny")         | `state.displayState`, `actions.approve`, `actions.deny`   | `displayState === 'pending-approval'`                                                                                             | `Button`'s own `cva` variants (`primary`/`destructive`), unaffected by this decision                                                      |
| `ToolCall.Response`        | `children` (formatted result text)                               | `state.displayState`                                      | `displayState === 'complete'` and `children` is truthy                                                                            | static styling                                                                                                                            |
| `ToolCall.DeniedNotice`    | `children` (denial copy)                                         | `state.displayState`                                      | `displayState === 'denied'`                                                                                                       | `--color-info`                                                                                                                            |
| `ToolCall.Error`           | `children` (error text)                                          | `state.displayState`                                      | `displayState === 'error'`                                                                                                        | `--color-negative`                                                                                                                        |

With this contract, `src/routes/_protected/index.tsx` composes one fixed JSX tree per `tool-call` part, passing `displayState`/`statusLabel`/`onApprove`/`onDeny` to `ToolCall.Root` and the actual content (name, arguments, response, denial/error copy) as `children` to each leaf — no descendant needs to know `getToolCallDisplayState`, `ToolCallPart`, or `@tanstack/ai` exist at all.

**Alternatives considered:**

- **Plain props on every child, no Context** (this plan's v1.0 decision). Reconsidered after implementation and direct user feedback: the "Context adds no value" judgment held only while `ToolCall` had a handful of children in the same file as its provider-equivalent logic; now that the family has grown, threading `part={part}` (and `onApprove`/`onDeny` on `ApprovalActions`) across every JSX line was assessed as real, avoidable repetition.
- A separate `cva`-variant-driven status-badge component instead of `data-*` + `group` selectors. Not chosen — the user picked the CSS-attribute approach specifically to keep styling declarative in `className` strings rather than introducing a second JS-variant mechanism alongside `Button`'s existing `cva` usage.
- Keeping `ToolCall.Name` responsible for both content branching (label/icon choice) and color computation via a style map (this plan's v1.0 `TOOL_CALL_NAME_STYLES` object). Removed — color now comes from CSS; the status label/icon content itself moved to the new `ToolCall.StatusBadge` (see next decision), so `ToolCall.Name` now only renders the tool name it's given.
- A generic `data-state` attribute name (matching common Radix/base-ui convention). Rejected — `@base-ui/react`'s own `Collapsible` primitives may independently set `data-state`/`data-panel-open`-style attributes for open/closed; reusing the same attribute name risks a silent collision. `data-tool-call-state` is deliberately namespaced to this feature's own state machine.

**Rationale:** Context removes the prop-repetition the user flagged; the `data-*`/`group` styling removes the JS style-map the user flagged as excess responsibility in `ToolCallName`; the file split addresses the user's observation that the compound component outgrew `chat-messages.tsx`. Each still respects the underlying goals of the v1.0 decision it supersedes (self-guarding children, no impossible boolean-flag combinations, one clean `ToolCallDisplayState` discriminant) — only the distribution mechanism (props vs. Context) and the color mechanism (JS map vs. CSS attribute) changed.

**Tradeoffs accepted:** Reintroduces a `createContext`/`use` API surface a future contributor needs to understand (mirrors `PromptInput.Root`, so it's not a novel pattern in this codebase). The `data-tool-call-state` attribute is a second place (alongside `ToolCallContext`) that carries `displayState` — kept in sync by construction since `ToolCall.Root` sets both from the same single `displayState` prop it's given, but worth a comment at the call site so a future edit doesn't update one and forget the other.

### Keep `ui/tool-call.tsx` decoupled from `@tanstack/ai` — data flows in as generic props/children, not `ToolCallPart`

**Decision:** `src/components/ui/tool-call.tsx` has **zero import** from `@tanstack/ai`, `@tanstack/ai-client`, or `@tanstack/ai-react`. It exports and consumes only its own `ToolCallDisplayState` type. The mapping from the library's `ToolCallPart` to this generic contract — `getToolCallDisplayState(part)` and the new `getToolCallStatusLabel(displayState)` — moves to `src/lib/ai/tool-call-display-state.ts`, called once by the route. Content that used to be read from `part` directly inside `ToolCallArgs`/`ToolCallResponse`/`ToolCallError` (v1.0) or via `state.part` from context (v1.1) is now passed as ordinary `children` by the route. The repeated status-indicator markup (spinner-or-dot + label span, previously duplicated across `ToolCallName`'s four non-`complete` branches) is extracted into a standalone `ToolCall.StatusBadge` that takes no label of its own — it reads `statusLabel` from context, and that string was supplied by the route via `ToolCall.Root`'s `statusLabel` prop, sourced from `getToolCallStatusLabel`.

**Alternatives considered:**

- Keep `ToolCallPart` (or a subset of it) flowing through `ToolCallContext`, as in v1.1. Rejected per direct user feedback: a UI component library under `src/components/ui/` should not know about a specific external SDK's data shape — that's business logic, and it also silently blocks this component from ever being reused for a differently-sourced "pending approval" UI (e.g., a future non-chat approval flow) without dragging in `@tanstack/ai` types.
- Leave the repeated status-indicator `<span>` block inline in `ToolCall.Name`, accepting the duplication across its four non-`complete` branches. Rejected — flagged directly as a "good candidate to extract" by the reviewer; the four blocks differed only in label text and spinner-vs-dot, both now externalized.
- Have `ToolCall.Root` accept a full `statusLabels: Record<ToolCallDisplayState, string>` map instead of a single pre-resolved `statusLabel` string. Considered and rejected as unnecessary indirection: the route already computes `displayState` once per part, so resolving the matching label at the same call site (one extra function call, `getToolCallStatusLabel(displayState)`) is simpler than handing the whole map down and making `StatusBadge` look up its own entry — the route doing the lookup keeps `ToolCall.Root`'s prop count small and each prop independently meaningful.

**Rationale:** This is the direct fix for the reviewer's core complaint — "think of these components as a library, not tied to any business logic." A component under `ui/` should be swappable onto a different data source without modification; the only way to guarantee that is for it to never import the data source's types. Bundled into the same decision because they share one root cause: `tool-call.tsx` was reaching into `ToolCallPart`-shaped data (via prop or context) instead of being handed already-normalized, generic values.

**Tradeoffs accepted:** The route now performs two explicit mapping steps per tool-call part (`getToolCallDisplayState`, then `getToolCallStatusLabel`) plus manual content formatting (JSON-stringifying `part.output`, extracting error text) inline, rather than a single `part` handoff. This is intentional — per the reviewer's framing, correctly mapping the external type onto the generic UI contract is explicitly the caller's responsibility, not the library's. `ToolCall.ApprovalActions`'s default "Approve"/"Deny" labels are English strings owned by the component (unlike the status labels) — treated as a reasonable UI-library default (comparable to a generic dialog defaulting to "OK"/"Cancel"), overridable via `approveLabel`/`denyLabel` props rather than forced fully generic, since unlike the four state labels there's no repeated-block duplication motivating extraction here.

### Remove the narrate-delete prompt instruction; add no new prompt instruction about approval

**Decision:** Delete the two sentences in `system-prompt.ts`'s "Acting with care" section that ask the LLM to narrate/confirm deletes in text and describe create/update/activate/pause as running immediately (per spec §7 constraint). Do not add new prompt text instructing the LLM on how to react to a denial.
**Alternatives considered:** Adding explicit prompt guidance like "if a tool result indicates the user declined, acknowledge briefly and ask what they'd like instead."
**Rationale:** The spec constraint only mandates removal (to avoid double-confirmation). The library already feeds the denial back as a normal tool-result message; general-purpose LLM behavior (already exercised via the rest of the system prompt's conversational tone) is expected to handle acknowledging a declined action without a dedicated instruction. Keeping the prompt diff minimal reduces risk of unintended behavior changes elsewhere in the prompt.
**Tradeoffs accepted:** If early manual testing (US-003 AC: "assistant can respond... rather than the turn simply ending") shows the model handles denial awkwardly, a short added instruction is a cheap follow-up — flagged as an open risk in §7, not pre-solved here.

### No test coverage added for the new UI in this pass

**Decision:** No Testing-Library component tests and no new Storybook stories are added for the Approve/Deny UI. Only the existing tool-definition shape tests (`tools/__tests__/*.test.ts`) and the chat route test (`chat.test.ts`) get updated assertions for the `needsApproval` flag, since those files already assert on tool/definition shape today.
**Alternatives considered:** Testing-Library tests for click-to-approve/deny interaction (would have been a new precedent, since no component currently has Testing-Library coverage — only Storybook stories exist for `ChatMessages`); Storybook-only visual coverage (matching existing precedent).
**Rationale:** Explicit user scope decision for this implementation pass.
**Tradeoffs accepted:** The approve/deny click-handler wiring (`ToolCall.ApprovalActions` calling `actions.approve`/`actions.deny` from context) and the self-guarding children's render conditions have no automated regression protection. This is a real gap given the feature exists specifically to prevent data-loss mistakes — flagged as an open risk in §7. The compound-component design (§6) at least makes each condition independently readable and small (a one-line `displayState === '...'` check per component, read from context), which lowers (but doesn't eliminate) the risk relative to a monolithic branch.

## 7. Open Questions & Risks

- [ ] **Risk — no automated coverage for approval UI.** Per explicit scope decision (§6), the Approve/Deny click path is untested. Likelihood: any future refactor of `ChatMessages` or the rendering switch could silently break the gate without a failing test. Mitigation: manual verification during `/implement` (approve and deny at least one call of each mutating tool type through the dev server) is required before considering this feature done, even without automated tests.
- [ ] **Risk — `approval.approved` persistence through the error-state transition is inferred, not explicitly documented.** The architecture docs describe the `approval` field being set by `addToolApprovalResponse` and describe the `TOOL_CALL_END` dual-role transition to `error` state as touching `output`/`state`, but do not explicitly confirm `approval.approved` survives that transition untouched. Mitigation: verify manually (deny a call, log/inspect the resulting part) early in `/implement`, before building the `denied` variant on top of it. If the assumption is wrong, fall back to the string-match alternative noted in §6, documented as a known fragility.
- [ ] **Open question — LLM's conversational handling of a denial.** §6 deliberately adds no new prompt instruction for this. If manual testing during `/implement` shows the model handles a declined tool call awkwardly (e.g., repeats the same call, or the turn stalls), revisit and add a short instruction — this would be a `/revise` to this plan's prompt-change scope, not a re-architecture.
- [ ] **Risk — v2 `data-tool-call-state` must not collide with `@base-ui/react`'s own Collapsible state attributes.** §6's styling decision assumes `data-tool-call-state` is a safe, unused attribute name on the `Collapsible.Root` DOM node. `/implement` should verify this against the installed `@base-ui/react` version (inspect rendered DOM or its source) before relying on `group-data-[tool-call-state=x]:` selectors — if base-ui already reserves that exact name, pick a different one (e.g. `data-approval-state`).
- [ ] **Migration risk — this is a rework of a fully-implemented, validated (PASS WITH FINDINGS) feature, not greenfield.** All 7 UI-facing tasks from the v1.0 implementation (`us001-01`, `us001-05`, `us001-06`, `us002-01`, `us003-01`, `us002-02`, `infra-01`) touch code this revision changes and must be re-implemented against the new file/Context/styling contract; the 4 non-UI tasks (`us001-02/03/04` tool-def flags, `us001-07` prompt edit) are unaffected and should not be re-opened. `/task` should regenerate against this plan version rather than patching the old task list in place, to avoid stale file-path references (`chat-messages.tsx`/`ChatMessages.ToolCall*` → `tool-call.tsx`/`ToolCall.*`, plus the new `src/lib/ai/tool-call-display-state.ts`).
- [ ] **Risk — content formatting logic moves into the route with no dedicated test.** `/implement` will need to inline `JSON.stringify(part.output)`, error-text extraction (`(part.output as {error?:string})?.error`), and denial copy directly in `src/routes/_protected/index.tsx` (or a small local helper) rather than inside a tested component. `getToolCallDisplayState`/`getToolCallStatusLabel` get unit tests in `src/lib/ai/__tests__/`; this last-mile formatting does not, consistent with §6's "no automated coverage for the new UI" scope, but worth flagging since it's arguably business logic too, just too small to warrant its own module.
