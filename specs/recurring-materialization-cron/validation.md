## Drift Findings

### Unmet requirements (spec → code)

- None at the spec/story level. All three Must Have stories (US-001, US-002, US-003) have full evidence and passing test coverage.
- Task-level gap: us001-01's acceptance criterion "Query uses the composite index `recurring_templates_status_next_due_date_idx` (verify via EXPLAIN)" has no corresponding test — no `EXPLAIN`/query-plan assertion exists anywhere in the suite. The index itself exists and is exercised functionally, but its actual usage by the SQLite query planner was never verified. Non-blocking at this app's scale, but the task's own AC is unmet as literally written.

### Scope creep (code → spec)

- `buildDueTemplatesQuery` (`src/lib/repositories/recurring-templates.ts:131-142`) is dead code: it is exported, documented as "for use inside runBatch transactions," but never imported or called anywhere (`runScheduledMaterialization` calls plain `listAllDueTemplates` directly, not batched). It exists solely to satisfy task us001-01's literal acceptance-criterion checkbox. Take to `/revise`: either find a real caller or remove it.
- No other scope creep found. Explicitly checked and confirmed absent: per-user timezone handling, a `failed → active` recovery path (`activateTemplate` still only allows `paused → active`), in-app notifications, recurring-template CRUD changes (routes under `src/routes/api/recurring-templates/` are untouched — confirmed via `git status`), a manual "run now" endpoint, and retry/backoff logic beyond the single failed-marking. No stray TODOs referencing any of these.

### Plan deviations

- Plan §6/Technical Decisions specify the new cross-user repository function should be named `listDueTemplates(now: Date)` per the task; the implementation instead named it `listAllDueTemplates(now)`, keeping `listDueTemplates(userId, now)` for the pre-existing per-user function. This is a sensible, intent-preserving deviation (avoids a same-name overload with a different signature/semantics in the same module) but is a literal mismatch against both plan.md's contract section and tasks.md's us001-01 acceptance criterion. Worth a one-line spec/plan update via `/revise` to keep the docs accurate, not a functional problem.
- Plan's Technical Decisions record the Option B choice (refactor `processDueRecurring` to share the catch-up loop) as an open question ("implementation should decide"); tasks.md documents the decision was made (Option B) in us001-02's "Design decision recorded" note. This is a plan open-question being resolved during implementation, which is expected — flagging only so `/revise` can fold the resolved decision back into plan.md for future readers.

### Convention drift

- None found. New code follows existing repository conventions (`list*`/`build*` naming apart from the one naming note above), service-layer error handling (`InternalError`/`NotFoundError`), colocated `__tests__/` structure, and the in-memory better-sqlite3 + real-migrations test pattern documented in plan.md §2.
- Minor, non-blocking observation: generated catch-up transactions use `source: "manual"` (`recurring-templates.ts:188`) — the `transactions.source` enum (`manual`/`chat`/`csv_import`) has no scheduler-originated value, and the spec's Non-Goals forbid changing the Transaction schema, so `"manual"` is the only schema-compliant choice. This predates this feature (pre-existing `processDueRecurring` already did this) and is not a new deviation — noted for awareness only.
- Minor, non-blocking observation: `processTemplateOccurrences`'s loop creates a transaction dated to `currentDue` before checking whether that occurrence itself already exceeds `end_date` (only the _next_ iteration's date is checked against `end_date`). This is pre-existing behavior inherited from the original single-occurrence logic, not introduced by this feature, and is only reachable via an edge case (e.g., `end_date` edited backward past an already-advanced `next_due_date`). Not in scope for this validation to require a fix, but worth a line in a future spec if it's ever hit in practice.
