# Spec: Recurring Template Scheduled Materialization

**Status:** Implemented
**Created:** 2026-07-12
**Version:** 1.0

---

## 1. Overview

Plata already lets users define recurring transaction templates (rent, subscriptions, salary) and already has the logic to turn a single due template into a posted transaction for one user (`processDueRecurring`). What's missing is the automation: nothing currently invokes that logic for anyone, on any schedule, across the whole user base. Today a recurring template just sits there — no transaction ever appears unless something manually calls the existing function. This spec covers making that materialization run unattended, for every user, on a fixed schedule, and covers the edge cases that arise once it's unattended: multi-day gaps, and templates that fail partway through.

## 2. Goals

- Every user's active, due recurring templates are materialized into real transactions automatically, on a recurring schedule, with no manual action required.
- A template that has missed multiple occurrences (e.g. the schedule didn't run for a few days) fully catches up: one transaction per missed occurrence, each dated to its original due date — not collapsed into a single catch-up transaction.
- A template that errors during materialization is marked `failed` and is excluded from all future automatic runs, so a broken template doesn't keep attempting (and potentially failing) indefinitely.
- The scheduled process covers all users in a single run — it is not scoped to one account.

## 3. Non-Goals

- **Per-user timezone handling.** Due-date comparisons stay UTC-only, exactly as the existing `advanceDueDate`/`computeNextDue` logic already works. A template becomes "due" at UTC midnight regardless of the owning user's actual timezone.
- **Recovering a `failed` template.** This spec introduces the first code path that ever sets `status = 'failed'`. Reactivating a failed template (e.g. extending the existing activate flow to allow `failed → active`) is explicitly out of scope and left for a follow-up. A failed template has no user-facing recovery path as of this spec.
- **In-app notifications.** No toast, badge, or notification-center entry when an automatic transaction is created. The transaction simply appears in the user's transaction list like any other, distinguishable only via its existing link back to the originating template.
- **Any change to recurring template CRUD** (create, edit, pause, cancel) — that surface already exists and is untouched by this spec.
- **A user-facing "run now" / manual trigger.** Verifying the schedule during development can rely on existing local tooling; this spec does not add an admin action or API endpoint for on-demand runs.
- **Retry/backoff policy beyond the single failed-marking.** No exponential backoff, no multi-attempt retry within a run — a materialization error marks the template failed immediately, once.

## 4. Roles & Actors

| Role      | Description                                                                                                                                                                                     |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| User      | Owns one or more recurring templates; configures amount, cadence, category, and start/end dates via the existing UI/API. Passively receives the transactions this feature creates.              |
| Scheduler | The unattended, system-level actor that runs on a fixed interval and performs materialization on behalf of every user in a single pass. Not a human role — represents the automated job itself. |

## 5. Domain Model

### RecurringTemplate (existing entity, behavior extended)

A user's rule for automatically generating a recurring expense or income.

- **Key fields:** `cadence` (daily/weekly/biweekly/monthly/quarterly/yearly), `next_due_date`, `last_insertion_date`, `status` (`active`|`paused`|`completed`|`failed`), `end_date`
- **Relationships:** belongs to one User; has many generated Transactions
- **Business rules:**
  - Only generates transactions while `status = active`.
  - When due (and one or more prior occurrences were missed), produces exactly one Transaction per missed occurrence, oldest first, each dated to its own original due date, until the template is caught up to the current time or its `end_date` is reached (at which point it becomes `completed`).
  - If materialization errors for this template (e.g. a referenced category no longer exists), the template becomes `failed` and is excluded from all future scheduled runs until further notice (recovery is out of scope — see §3).

### Transaction (existing entity, unchanged)

A single financial event, either entered directly by a user or generated by a template.

- **Key fields:** `amount`, `date`, `recurring_template_id` (nullable link back to the originating template)
- **Relationships:** optionally originates from one RecurringTemplate
- **Business rules:** a given (template, original due date) pair produces at most one Transaction — re-running the schedule must never duplicate a transaction already created for an occurrence.

### Scheduled Run (new concept — the sweep itself, not a stored entity)

One execution of the automated job, covering every user's due templates.

- **Conceptually carries:** the run's reference time ("now"), and a per-template outcome (transaction(s) created / caught up / marked failed).
- **Business rule:** a single run must cover all users with due templates, not just one account — this is what's net-new versus the existing per-user `processDueRecurring` logic.

## 6. User Stories

### [US-001] Automatic materialization across all users

**Priority:** Must Have
**Actor:** Scheduler

> As the Scheduler, I want to materialize all due recurring templates for every user on a fixed schedule, so that recurring transactions post without anyone manually triggering it.

**Acceptance Criteria:**

- [ ] On each scheduled run, every active template across every user whose `next_due_date` is at or before the run's reference time is considered for materialization.
- [ ] A user with no due templates is unaffected by the run (no-op for that user).
- [ ] The run requires no per-user or manual initiation — it happens on a recurring, fixed schedule.

---

### [US-002] Full catch-up after missed occurrences

**Priority:** Must Have
**Actor:** User

> As a user whose template missed one or more scheduled runs, I want every missed occurrence to appear as its own backdated transaction, so my transaction history is complete and accurate rather than collapsed or skipped.

**Acceptance Criteria:**

- [ ] If a template is overdue by N occurrences when a run finally processes it, exactly N transactions are created, each dated to its own original due date.
- [ ] After catch-up, the template's `next_due_date` reflects the next occurrence after "now," and `last_insertion_date` reflects the run time.
- [ ] If catching up would carry the template past its `end_date`, it stops at the last valid occurrence and becomes `completed`, same as existing single-occurrence behavior.
- [ ] Re-running the schedule again immediately afterward does not create duplicate transactions for occurrences already materialized.

---

### [US-003] Fail a template on materialization error

**Priority:** Must Have
**Actor:** User

> As a user whose template hits an error during materialization (e.g. its category was deleted), I want the template marked failed and left alone going forward, so a broken template doesn't keep attempting and potentially corrupting my data on every subsequent run.

**Acceptance Criteria:**

- [ ] If materializing a given template raises an error, that template's `status` becomes `failed`.
- [ ] A `failed` template is excluded from consideration on all subsequent scheduled runs.
- [ ] An error on one user's template does not stop the run from processing other users' or other templates' due occurrences in the same pass.

---

## 7. Constraints

- Must reuse the existing `recurring_templates` and `transactions` schema and the existing per-template materialization semantics (`advanceDueDate`, `computeNextDue`) — no new tables for the core domain model.
- Must not duplicate a transaction for an occurrence that was already materialized, even if the scheduled run is invoked more than once for the same due date (the underlying execution environment does not guarantee exactly-once invocation).
- Must work within the existing Cloudflare Workers + D1 architecture already used by the rest of the app (no new infrastructure/services).

## 8. Non-Functional Requirements

| Category    | Requirement                                                                                                                                                |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reliability | A run must be safe to invoke more than once for the same reference time without creating duplicate transactions or double-advancing a template's due date. |
| Reliability | A failure while processing one user's templates must not prevent other users' due templates from being processed in the same run.                          |

## 9. Open Questions

- [ ] **Recovering a `failed` template.** Out of scope per §3, but a template with no recovery path is a real product gap the moment this ships — who owns deciding when/how that follow-up spec happens?
- [ ] **Schedule frequency** (e.g. daily vs. hourly) is a technical decision deferred to `/plan`, but it has a user-facing consequence worth flagging here: a coarser schedule means a template can appear "late" by up to the schedule's interval before catch-up (§US-002) fires. Confirm the acceptable worst-case lateness when the plan proposes a frequency.
