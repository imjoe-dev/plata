# Session Approval is enforced server-side via twin tool-definition variants, not client-side auto-response

Status: accepted

Users can grant Session Approval so create/update Mutating Tools stop prompting for the rest of that Chat Session (delete tools always prompt — see `CONTEXT.md`). `@tanstack/ai`'s `needsApproval` is a static `boolean` on a `ToolDefinition` with no predicate/context-aware form (confirmed against its docs), and `addToolApprovalResponse` is a bare `{id, approved}` RPC with no "remember this" concept — so nothing here comes for free from the library.

We rejected having the client silently auto-respond to every future `approval-requested` part once the user clicks through once: that keeps the server-side tool definitions permanently gated, meaning the "approval" is really just the client agreeing with itself, with no server-side record that the session was ever elevated. Instead, Session Approval is a persisted boolean on `chat_sessions`. Cloudflare Workers are stateless per-request, so this can't live in memory between requests — it has to be a column, read once per `/api/chat` POST before `chat()` is called (it comes for free off the row `getOrCreateSession` already fetches/creates — no extra lookup). Based on that flag, the route picks between two module-scope tool arrays for create/update/`update_user_preferences` tools — one gated (`needsApproval: true`), one not — built once at load time, consistent with ADR-0004's "tools stay defined once at module scope" guarantee: selection between two pre-built arrays per request, not per-request construction. Delete tools have no ungated variant at all — `needsApproval: true` is unconditional on them, regardless of the flag.

One consequence of deciding per-request, not per-tool-call: if the LLM makes several distinct mutating calls within a single reply and the user grants Session Approval on the first one, the flag only takes effect starting the _next_ `/api/chat` request — the tools array for the in-flight request was already built before the click. The remaining calls in that same reply would still show individual prompts under this scheme alone. We accept that gap server-side and paper over it client-side: once "Approve for this session" is clicked, the client also remembers it in memory for the remainder of the current stream and auto-responds to further `approval-requested` parts in that same turn — **except** for delete tools, which the client identifies by their `delete_` name prefix and always still prompts, even mid-bridge. This client-side bridge is deliberately scoped to "rest of this turn" only, and is not itself the approval authority — the persisted flag is.

Session Approval is a one-way door: there is no revoke UI. `MUTATION_RATE_LIMITER` (ADR-0004) is unaffected either way — it guards burst volume, a different failure mode than unreviewed action, and stays in force whether or not the session is approved.

The approval prompt itself deliberately breaks `components.md`'s "no more than two actions in a row" convention (dialog footers cap at two buttons, toasts get one action, empty states never show two): Approve / Approve for this session / Deny is a three-button row. This is a conscious, scoped exception for this one prompt, not a precedent — don't generalize it to other action rows.

**Revisit when:** a revoke path is actually needed, or per-resource (rather than blanket) approval scope becomes necessary.
